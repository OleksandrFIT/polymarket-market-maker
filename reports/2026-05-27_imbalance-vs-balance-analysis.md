**Дата**: 2026-05-27, ~22:49 UTC
**Контекст**: користувач припустив що "якщо хоч 1 сторона не filled — буде великий мінус".

---

## ⚠️ TL;DR

**Гіпотеза «треба filling обидві сторони» — НЕПРАВИЛЬНА.**

Реальні дані показують зворотне: найприбутковіші ринки твого бота — ті, де
сильний `imbalance` (одна сторона набагато більша за іншу). Bonereaper заробляє
не через «balance», а через **бімодальний патерн** — або повністю-imbalanced
(коли ринок trending), або повністю-balanced (коли choppy). Твій бот завжди
посередині = неефективно.

## 🧠 Що це означає для стратегії

### Поточний `compute_ladder` — структурна проблема

```python
# Зараз: симетричні розміри обох сторін
yes_quotes = [Quote('YES', mid_yes - 0.01, 10), ...]
no_quotes  = [Quote('NO',  mid_no - 0.01, 10), ...]

# + жорсткий ліміт на skew
if abs(yes_qty - no_qty) > 500:
    skip_dominant_side  # ← БЛОКУЄ накопичення winning side!
```

### Що робить Bonereaper

1. **Книга веде його, не навпаки** — дозволяє imbalance розвинутися
2. Коли ринок trending → накопичує 1000+ shares ОДНІЄЇ сторони
3. Коли ринок choppy → накопичує обидві сторони balanced (для merge)
4. Активно **збільшує квоти на winning side**, не закриває losing

2. **Directional size skew** — посилити winning side
   ```python

       yes_size_mult = 1 + (mid_yes - 0.5) * 4  # 0.6→1.4x, 0.8→2.2x
       no_size_mult = 1 / yes_size_mult
   ```

3. **Динамічний budget** — більше капіталу в trending markets
   ```python

   ```

4. **Прибрати directional_filter** (Phase-8 фікс) — він обрізав можливість
   стати imbalanced. Замість «skip losing side» — робити «smaller losing,
   bigger winning».

## 📈 Очікувані результати — простою мовою

### 💚 Pros

| Покращення | Конкретно |

## ⚠️ Критичне застереження

**Paper-симуляція все одно дає FAKE fills (100% rate).** Зміна підсилює
розмір ставок — але якщо в LIVE у нас 5-15% fill rate (через queue
priority), то реальний результат буде:
- Менше fills загалом → менша експозиція
- Кожен fill вищого розміру → ризик per fill більший
- Net: **невідомо краще чи гірше**

### Рекомендую: НЕ робити цю зміну до live-тесту

Чому: ми зараз оптимізуємо на фейкових даних. Без live verification ми не
знаємо чи 65% accuracy на mid prediction зберігається при реальних
маленьких fill rates. Збільшення розміру ставок без знання реального
hit rate = чисте збільшення variance без покращення EV.
