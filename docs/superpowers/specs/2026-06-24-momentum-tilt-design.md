# Spec: Momentum-tilt + страхова нога + circuit-breaker (Крок 1)

**Дата:** 2026-06-24
**Статус:** затверджено до реалізації
**Контекст пам'яті:** [[project-momentum-edge]], [[project-competitor-verdict]], [[reference_guru_wallet]]

## 1. Мета й обґрунтування

Перевести бота з поточної −EV конфігурації (deep-ladder, що ловить падаючу
дешеву ногу й тримає її) на доказово прибуткову трикомпонентну стратегію, яку
ми реконструювали з реальних угод конкурента (гаманець 0xb945…db68 = `l5Zn1bWoM8eTsK`)
і підтвердили бектестами.

**Доказова база (сесія 2026-06-24):**
- Reversal/deep-leg «ловити дешеву ногу на розворот» — −EV на кожному рівні
  (`_deep_dip.py`, 900 вікон): нога @ $0.05 виграє 1.9%, @ $0.10 — 5.5%.
- Momentum/favorite tilt — +EV, виживає taker-спред до 3¢ (`_momentum_robust.py`,
  пул 3000 вікон, берез–черв): min10 +4.7¢/share @ 2¢ slip, hit 88%.
- Live `trend_detector` валідовано (`_validate_detector.py`): його win_prob-модель
  = простий поріг руху на хв10 і краще на хв12. Використовуємо наявний `detect_bias`.
- Дешева протилежна нога = СТРАХОВКА (`_hedge_analysis.py`, 24h): гасить вікна-розвороти
  з −$393 до −$61/вікно; сама по собі −EV (премія), але різко знижує дисперсію.
- Конкурент НЕ детектує режим — він завжди тримає страхову ногу і торгує всі вікна.
- Maker/taker (інференс ціна-vs-mid, 3058 трейдів 24h, `_maker_taker.py`): дешеві ноги
  (ціна <0.5) бере переважно **maker** (ліміт-біди), фаворита 0.5–0.8 — переважно **taker**.
  Це підтверджує дизайн: база/страховка = ліміт-maker (`plan_ladder`), tilt = taker (FAK).

**Три потоки прибутку/захисту:**
1. **База (merge-maker):** обидві сторони лімітками, пари < $1 → стабільна добавка (~30%).
2. **Tilt (directional):** докуповування переможця за сигналом BTC → головний прибуток (~70%).
3. **Страхова нога:** помірний дешевий лузер (утворюється з бази) → захист від розворотів.
4. **Circuit-breaker:** backstop — пауза tilt, якщо едж тимчасово зник (боковик).

## 2. Ключове узгодження: пригнічення лузера vs страховка

Зараз `trend_bias` повністю прибирає рунги сторони-лузера (`ladder_planner.py:117–119`).
Це конфліктує зі страховкою (страховка = трохи дешевого лузера). Рішення:

- **Базова сітка НЕ пригнічує лузера повністю** — лишає його помірно, у межах `naked_cap`,
  що й формує страхову ногу.
- **Роль детектора змінюється:** він більше не глушить базу, а лише вказує, кого
  докуповувати в tilt (переможця).
- **Захист від −EV-перебору дешевого лузера** (наш ранній висновок про deep-dip)
  забезпечує не пригнічення, а `naked_cap` + те, що tilt тримає нас нетто-лонг у переможці,
  + вимкнений `deep_ladder` (більше не ллємо необмежено в глибокий хвіст).

Три потоки + backstop, чітко розділені: **база → пари + страховка**, **tilt → переможець**,
+ контроль **circuit-breaker → пауза tilt у боковику** (це контроль, не потік).

## 3. Підхід до інтеграції

Обрано: **pure-планер `plan_tilt()` + невеликий блок у наявному `_ladder_window`**
(той самий патерн, що блок completion). Перевикористовує весь наявний каркас
(опитування книг, локальний інвентар, каппи, cleanup `cancel_all`). Базова сітка
(`plan_ladder`) і блок completion лишаються. Мінімум нового коду.

Відкинуто: окремий `_momentum_window` (дублює ~150 рядків каркасу), пряме
під'єднання `hedge_planner` без обгортки (сайзинг завеликий для $15).

## 4. Компоненти

### 4.1 `quoter/runner/tilt_planner.py` (новий, чистий)
**Призначення:** скільки часток переможця докупити цього тіку.
**Інтерфейс:**
```
plan_tilt(tbias: str, fav_ask: float, inv_fav: float, spent: float,
          per_window_cap: float, step: int) -> float
```
- `tbias`: "UP" | "DOWN" | "NEUTRAL" (з `detect_bias`). NEUTRAL → 0.
- Сайзинг: ціль — `favorite_shares ≈ spent` (математика з `hedge_planner.hedge_buy_qty`:
  `q = (spent − inv_fav) / (1 − fav_ask)`), але обрізана:
  - кроком `step` (малі дольки за тік, як `complete_step`);
  - залишком бюджету `per_window_cap − spent` поділеним на `fav_ask`.
- Повертає 0, якщо вже достатньо переможця, ask недоступний, або бюджет вичерпано.
- **Чистий, без I/O. Юніт-тести.**

### 4.2 `quoter/runner/regime_tracker.py` (новий, чистий) — CB на realized tilt-P&L

**Чому НЕ hit_rate (виправлення блокера з рев'ю, верифіковано емпірично):**
вхід фаворита на хв10/conf0.35 = **avg 0.815**, точка беззбитковості (з 2¢) = **0.835**,
edge лише **+4.7¢/share** із запасом ~4.7 п.п. hit-rate. Поріг на hit_rate (напр. 0.58)
тримав би tilt увімкненим у −EV-смузі 0.58–0.835 — детектор «правий» у 70%, а угоди
збиткові. Тому CB міряє **paper tilt-EV на частку**, а не hit_rate (який сліпий до
ціни входу). hit_rate лишається лише діагностикою.

**Інтерфейс:**
```
class RegimeTracker:
    def __init__(self, window: int = 20, min_samples: int = 12,
                 min_ev: float = 0.01, fee: float = 0.02)
    def record(self, predicted_fav: str, entry_price: float, winner: str) -> None
    def paper_ev(self) -> float | None     # сер. (1-(entry+fee)) якщо вгадав, інакше -(entry+fee)
    def hit_rate(self) -> float | None     # ДІАГНОСТИКА, не для рішення
    def directional_enabled(self) -> bool  # True ЛИШЕ якщо samples >= min_samples І paper_ev >= min_ev
```
- Черга останніх `window` трійок `(передбачений_фаворит, ціна_входу_фаворита_на_момент_рішення, переможець)`.
- `paper_ev` рахує EV/share саме tilt-угоди з урахуванням `fee` — прямо бачить ціну входу.
- **Shadow-only warm-up:** доки `samples < min_samples`, `directional_enabled()=False`
  (tilt НЕ виконується), але record() усе одно накопичує paper-дані. Це безпечно після
  рестарту (трекер in-memory): після перезапуску знову прогрів на shadow, tilt вимкнено,
  поки paper-EV не підтвердить едж. (Персист черги — опційно, §9.)
- `record` пишеться НАВІТЬ коли tilt не виконувався (shadow), щоб бачити відновлення.
- **Чистий, без I/O. Юніт-тести.**

### 4.3 `quoter/runner/merge_runner.py` (зміни в `_ladder_window`)
- Біля рядка 561 (після `tbias = self._trend_bias(...)`):
  - `enabled = self._regime.directional_enabled()`
  - **no-tilt cutoff:** не виконувати tilt у останні `cfg.tilt_cutoff_sec` (напр. 45с)
    вікна — щоб taker-FAK не клався впритул до cleanup/`cancel_all`.
  - якщо `cfg.tilt_enabled and enabled and tbias != "NEUTRAL" and time_remaining > tilt_cutoff_sec`:
    - визначити сторону переможця (UP→YES, DOWN→NO), її `inv_fav`, `fav_ask`;
    - **стеля ціни:** якщо `fav_ask > cfg.tilt_max_price` → tilt пропустити (не палити комісію по 0.95+);
    - `cq = plan_tilt(tbias, fav_ask, inv_fav, realized, cfg.per_window_cap, cfg.complete_step)`;
      (бюджет `per_window_cap − realized` обчислюється ЩОТІКУ → кумулятивно безпечно при кількох викликах за вікно);
    - якщо `cq > 0` → taker-buy **FAK** (`post_only=False`, `order_type="FAK"`) переможця.
      FAK (не FOK) дає часткове виконання на тонкому стакані — не пропускаємо найсильніші рухи;
    - записати ціну входу фаворита (`fav_ask`) для подальшого `regime.record`;
    - облік у `posted`/`committed`, лог `runner_tilt`.
- **Базову сітку (`plan_ladder`) НЕ глушити по тренду** — передавати `trend_bias="NEUTRAL"`
  у `plan_ladder` (або відповідний прапор), щоб лузер-нога лишалась як страховка;
  напрямок використовується ТІЛЬКИ для tilt.
- Наприкінці вікна:
  - **Переможець** визначається з фінальної ціни на `END_BUFFER_SEC` до кінця:
    останній mid YES ≥ 0.5 → "Up" (YES), інакше "Down" (NO). (Те саме правило, що в
    бектесті; on-chain resolution прийде пізніше й не потрібне для circuit-breaker.)
  - **Записувати лише вікна з directional-калом:** зберігати останній НЕ-NEUTRAL
    `tbias` і ціну фаворита на момент того сигналу (`last_bias`, `last_fav_entry`);
    якщо сигнал був → `self._regime.record(last_bias, last_fav_entry, winner)`.
    `last_fav_entry` — це fav_ask на момент сигналу (paper-вхід), щоб paper-EV рахувався
    на тій самій шкалі, що й рішення. Вікна без сигналу у tracker не пишуться.
  - **Калібрування шкали:** paper-EV рахується від mid/ask-проксі; live реальний edge
    звіряти з фактичними філами (§8) — абсолютний рівень може відрізнятись.
- `self._regime = RegimeTracker(cfg.regime_window, cfg.regime_min_samples, cfg.regime_min_ev, cfg.tilt_fee)` в `__init__`.

### 4.4 `quoter/config.py` + `quoter/runner/run_control.py`
Нові поля `Config`:
- `tilt_enabled: bool = False` (за замовч. вимкнено; вмикається в run_control)
- `tilt_cutoff_sec: float = 45.0` (no-tilt буфер наприкінці вікна)
- `tilt_fee: float = 0.02` (оцінка taker-спреду для CB та сайзингу)
- `tilt_max_price: float = 0.90` (стеля ціни tilt: не доганяти фаворита taker'ом вище —
  по 0.95+ це майже чиста комісія на тонкій маржі; точне число калібрується реплеєм.
  Купівлі конкурента по ~0.98 — це доповнення пар, окрема логіка, не tilt.)
- `regime_window: int = 20`
- `regime_min_samples: int = 12`
- `regime_min_ev: float = 0.01` (мін. paper-EV/share, щоб тримати tilt увімкненим)
- `insurance_frac: float = 0.25` (цільова частка $-експозиції на страхову/лузер-ногу)

**Роль `naked_cap` уточнена:** він обмежує лише дисбаланс БАЗИ; tilt свідомо робить нас
нетто-лонг у переможця ПОНАД naked_cap (тому tilt-buy не g-ється naked_cap'ом, лише
`per_window_cap`/`posted`). Страховка (лузер-нога) розмірюється окремо як `insurance_frac`
від експозиції, НЕ плоским naked_cap. Точні числа (`insurance_frac`, ціновий діапазон
страховки) калібруються реплей-харнесом (§7) проти −$61/вікно з `_hedge_analysis`.

**`min_buy_price` переглянуто:** конкурент бере страхову ногу avg **$0.32 (нижче 0.42)**;
жорсткі 0.42 зробили б нашу страховку дорожчою за його й не перенесли б −$61. −EV-висновок
deep-dip стосувався РОЗМІРУ перебору на 0.05–0.10, не порога. Тому: дозволити страховку
дешевшою (поріг ~0.15–0.30), але з обмеженим РОЗМІРОМ (`insurance_frac`); точне число —
з реплею. У тексті «дешева» → «помірна страхова нога».

Значення в `run_control.py` CFG (Крок 1A + 1B + ризик):
- `deep_ladder=False`, `min_buy_price` ← калібрується реплеєм (стартова гіпотеза ~0.20)
- `rungs=2`, `rung_spacing=0.03`, `naked_cap=5` (бар'єр БАЗИ)
- `per_window_cap=15.0`, `per_market_cap_usd=15.0`, `max_inflight_rungs=1`, `flat_size=5`, `rung_size=5`
- `trend_enabled=True`, `trend_confidence=0.35`, `trend_gate_sec=600.0`
- `complete_pairs=True`, `complete_continuous=True`, `complete_step=10`, `sell_fallback=False`
- `tilt_enabled=True`, `tilt_cutoff_sec=45.0`, `tilt_fee=0.02`
- `regime_window=20`, `regime_min_samples=12`, `regime_min_ev=0.01`, `insurance_frac=0.25`

## 5. Потік даних

```
Binance WS → _btc_buf → _trend_bias(strike, time_left) → tbias
                                            │
        regime_tracker.directional_enabled()│
                                            ▼
   (tbias≠NEUTRAL & enabled) → plan_tilt → taker-buy переможця ──┐
                                                                  ├→ інвентар нетто-лонг переможця
   plan_ladder (обидві сторони, БЕЗ trend-пригнічення) → пари + помірна страхова нога ┘
                                            │
                          кінець вікна → визначити переможця → regime_tracker.record(...)
```

## 6. Обробка помилок / безпека

- Усе під наявними каппами: `per_window_cap`, posted-backstop (`post_cap`), FORCE STOP,
  cleanup `cancel_all` у `finally`.
- Tilt — taker **FAK** (часткове виконання на тонкому стакані); якщо немає ask або
  бюджет вичерпано → `plan_tilt`=0.
- **no-tilt буфер:** жодних tilt-FAK у останні `tilt_cutoff_sec` (45с) — не класти taker
  впритул до cleanup/`cancel_all`.
- Нема даних Binance/детектора → `tbias=NEUTRAL` → tilt не діє, база працює.
- Старт завжди STOPPED; оператор тисне START на дашборді.
- Tilt-докупівля переможця окремо обмежена `per_window_cap`, як і completion-taker
  (рядок 519): `budget_left = per_window_cap − realized`, рахується щотіку (кумулятивно).

## 7. Тестування

Три шари:

1. **Юніт:** `tilt_planner` (сайзинг до «≈spent», межа кроку, межа бюджету, NEUTRAL→0,
   fav_ask→1 без діління на нуль); `regime_tracker` (**shadow-only warm-up: вимкнено
   поки samples<min_samples**, paper_ev≥min_ev вмикає, падіння нижче вимикає, вікно
   витісняє старі семпли, paper_ev враховує fee/ціну входу). Плюс **no-peeking**:
   assert, що `plan_tilt` на момент `t` НЕ торкається даних, відомих лише на `t_close`.

2. **Детермінований реплей-харнес** (`scripts/_replay_tilt.py`, новий): прогнати РЕАЛЬНІ
   `regime_tracker` + `plan_tilt` (імпорт із бота) по пулу історичних вікон (кеш є),
   щоб виміряти на коді, а не на формулі:
   - частоту хибних пауз CB на трендових даних (скільки +EV-вікон CB вимикає даремно);
   - що сайзинг `plan_tilt` дає очікуваний +EV (звірка з +4.7¢/share бектесту);
   - реальний `avg_fav_entry` для калібрування `regime_min_ev`/`tilt_fee`;
   - калібрування `insurance_frac` + цінового порога страховки проти −$61/вікно.
   Це квантова валідація самого коду перед грошима; дешево (дані + чисті планери є).

3. **Інтеграція (`_ladder_window`):** як решта live-шляху — оператор-gated малий live
   ($15/вікно, BTC 15m), не автотест.

- Уся наявна тестова база має лишатись зеленою.

## 8. Метрики live-валідації (після запуску)

- realized fill price переможця vs бектест (ціль: tilt дає +EV після спреду);
- hit-rate детектора live vs ~88% з бектесту;
- внесок tilt vs база vs страховка в PnL (ціль ~70/30 + страховка ≈ −EV-премія);
- спрацювання circuit-breaker (як часто пауза, чи коректно) — це ПЕРВИННИЙ автоматичний
  захист (пауза tilt при paper-EV < `regime_min_ev`), спрацьовує до значних втрат.
- **Стоп-критерії (ручний backstop, довший горизонт):** realized edge < 0 на 100+ вікнах,
  або реальний `avg_fav_entry`/fill значно гірший за бектест (0.815) → перекалібрувати або стоп.

## 9. Відкриті ризики

- **Тонкий edge:** запас лише ~4.7 п.п. hit-rate (88.2% проти беззбиткових 83.5%) і
  +4.7¢/share. Невеликий зсув режиму стирає едж — тому CB на paper-EV і страховка критичні.
- **Боковий режим недосемпльований** (n80 у бектесті, всі 4 місяці = тренд).
  Захист — страхова нога + circuit-breaker; остаточно підтвердиться лише live.
- **Warm-up після рестарту:** трекер in-memory → рестарт скидає чергу → shadow-only
  прогрів (tilt вимкнено), поки знову не набереться `min_samples`. Безпечно, але tilt
  «мовчить» ~12 вікон після кожного рестарту. Персист черги (SQLite/Mongo) — опційний фікс.
- **FAK-пропуск на тонкому стакані:** якщо ask знятий саме на сильному русі, FAK
  виконається частково або нуль — можливий пропуск частини найкращих рухів. Прийнятно
  (краще недокупити, ніж купити дорого), але tilt може «мовчати» на піках.
- `trend_detector` написаний для 5m; для 15m sigma-fallback масштабується як `tl/300`.
  Працює (валідовано), але варто перевірити поведінку в перші/останні хвилини вікна.
- Circuit-breaker реактивний (лаг ~12–20 вікон) — страхова нога покриває проміжок.

## 10. Поза обсягом (YAGNI)

- Колокація us-east-1 (не потрібна: ліміт-біди стоять заздалегідь, latency не критична).
- Авто-merge/redeem on-chain (поки вручну, як зараз).
- API-детектор reversal-режиму (варіант С) — відкинуто на користь circuit-breaker.
- Масштабування розміру — окремий крок після live-валідації.

## ADDENDUM 2026-06-25 — directional-first ребаланс (за результатом combined-сим)

Перед live прогнали офлайн-симулятор УСІЄЇ інтегрованої стратегії (`scripts/_strategy_sim.py`,
~1960 вікон). Перша версія (база-важка, tilt-сайзинг «favorite ≈ spent») дала **майже нуль**:
+$0.036/вікно, +0.40% обороту, Sharpe ~0.02, tilt спрацьовував лише в 13% вікон.

**Причина (структурний баг сайзингу):** правило `favorite_shares ≈ spent` залежить від
масштабу — `spent` у $, `inv_fav` у штуках. При $15/вікно spent($9) ≈ inv_fav(8 шт) →
`gap≈0` → tilt майже не докуповує. У конкурента spent=$300 ≫ штук → працює. На малому бюджеті — ні.

**Фікс:** tilt сайзиться за **$-часткою** цілі: `target_$ = tilt_frac × per_window_cap`
(директивно directional-first), а не за «≈spent». Плюс менша база (`rungs=1`, `naked_cap=3`),
щоб вона не з'їдала бюджет до tilt.

**Результат сим (directional-first, tilt_frac=0.65):** +$0.576/вікно, **+8.0% обороту**,
win 86%, Sharpe ~0.20, tilt 36% вікон, 37% капіталу в переможця, ~+$36/день @ $15. **10× краще.**

**Застереження:** +8% — оптимістично (ідеальні філи в сим, без черги/часткових); реалістично
ближче до виміряних **4% конкурента**. При його $300/вікно × 4% × ~63 вікна ≈ **+$760/день** —
його профіль. Шлях: довести на малому → нарощувати бюджет/вікно.

**Зміни коду (гілка feat/tilt-directional-first):** `plan_tilt` сигнатура
`(tbias, fav_ask, fav_cost, spent, per_window_cap, tilt_frac, step, max_price)`;
`Config.tilt_frac=0.65`; `run_control`: `rungs=1, naked_cap=3, tilt_frac=0.65`.
Це ЗАМІНЮЄ опис сайзингу в §4.1 («favorite ≈ spent» → $-частка).
