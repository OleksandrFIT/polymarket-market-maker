# Чек-лист деплою в us-east-1 (підготовка — БЕЗ live-торгівлі)

**Мета:** перенести poly-quoter в AWS us-east-1, щоб скоротити RTT ~110 мс → одиниці мс,
аби наповнювались **обидві** merge-ноги і виміряний едж 1–2¢/пару став ловимим. Цей
чек-лист — **лише підготовка + вимірювання**, він НЕ вмикає live-торгівлю. Перехід на
реальні гроші — окреме, свідоме рішення (див. §7).

Про секрети: посилайся на ключі `.env` лише за ІМЕНАМИ (POLY_PRIVATE_KEY, POLY_API_KEY,
POLY_API_SECRET, POLY_PASSPHRASE). Ніколи й ніде не вставляй їхні значення.

---

## 1. Інфраструктура
- [ ] EC2-інстанс у **us-east-1** (N. Virginia). Почни з малого: `c7i.large` /
      `c6i.large` (compute-optimized, стабільний такт). Апгрейд лише якщо впрешся в CPU.
- [ ] Обери **availability zone** з найменшою латентністю до ендпойнта CLOB
      (зміряй у §2 з 2–3 AZ, лиши найкращу).
- [ ] Ubuntu 22.04/24.04 LTS, Python 3.11 (як локально), `.venv` з тими ж залежностями
      (`pip install -e .` / зафіксований requirements).
- [ ] Синхронізація часу: увімкнений `chrony` (точний годинник важливий для таймінгу
      вікон і логів).
- [ ] Відкрити вихідні HTTPS/WSS до `clob.polymarket.com`,
      `ws-subscriptions-clob.polymarket.com`, `data-api.polymarket.com`,
      `gamma-api.polymarket.com`, `stream.binance.com` (Binance лише якщо колись
      знадобиться; merge-мейкеру він не потрібен).

## 2. Зміряти РЕАЛЬНУ латентність до CLOB (заради чого все)
- [ ] HTTP RTT: `for i in $(seq 20); do curl -o /dev/null -s -w "%{time_connect} %{time_total}\n" https://clob.polymarket.com/time; done` — записати медіану connect + total.
- [ ] WS round-trip: під'єднатись до `wss://ws-subscriptions-clob.polymarket.com/ws/market`,
      заміряти цикл subscribe→перший book-update; записати медіану.
- [ ] DNS/маршрут: `mtr -rwzbc100 clob.polymarket.com` — підтвердити мало хопів, без
      виходу трафіку з us-east-1.
- [ ] **Ціль:** book-update RTT ≤ ~10 мс. Якщо досі десятки мс — спробуй іншу AZ /
      сімейство інстансів, перш ніж рухатись далі.
- [ ] Запиши цифри — вони замінять припущення `paper_latency_ms=110`, зашите в модель
      філів.

## 3. Перевірити чергу + економіку комісій (едж тонкий — 1–2¢)
- [ ] Підтвердити **maker**-економіку Polymarket: post-only ордери і поточну
      **maker-комісію** (має бути ~0 або ребейт — будь-яка taker-комісія вб'є 1¢-едж).
- [ ] Підтвердити вартість on-chain **merge**: `mergePositions` — це L2-транзакція
      (Polygon); газ за merge має бути « зафіксований спред за партію. Батчити merge,
      щоб амортизувати газ.
- [ ] Саніті: перезапустити `scripts/_live_merge_feasibility.py` ІЗ сервера —
      підтвердити, що `bid_Up + bid_Down < $1` досі тримається, і зміряти доступну
      глибину на нашому розмірі.

## 4. Тюнінг застосунку під латентність (лише конфіг, досі paper)
- [ ] Спершу перезапустити paper НА сервері. Знизити `requote_min_interval_ms`
      (зараз 50) ближче до нового RTT; зпрофілювати async-цикл, щоб наша власна обробка
      не була вузьким місцем.
- [ ] Виставити в моделі філів `paper_latency_ms` на **зміряне** значення (§2) і
      `paper_queue_position` на реалістичне місце — щоб paper відображав нову реальність,
      а не Словаччину.
- [ ] Перезміряти поведінку paper: гола експозиція має лишатись біля нуля, а **обидві**
      ноги — починати наповнюватись (модель показуватиме merge на реальних парах).
- [ ] Лише після цього розглянути послаблення `max_naked_shares` ближче до толерантності
      конкурента (низька латентність робить наколку безпечною).

## 5. Надійність (має працювати 24/7)
- [ ] Запуск під `systemd` (або supervisor) з авто-рестартом; stdout у логи.
- [ ] Перевірити авто-реконект WS + поведінку `ws_stale_timeout_sec` під примусовим
      розривом.
- [ ] Дашборд доступний (SSH-тунель або закрита security group — НЕ виставляти дашборд
      публічно).
- [ ] Підтвердити, що `RiskGuard` робить halt на `max_daily_loss_usd`; виставити
      консервативно.
- [ ] Ротація логів; диск під ріст `state.db`; щоденний бекап `state.db`.

## 6. Валідація paper у us-east-1 (go/no-go ПЕРЕД будь-якою розмовою про live)
Запустити paper на сервері на значущий проміжок і підтвердити:
- [ ] Обидві ноги наповнюються (не лише падаюча) → merge спрацьовує на реальних
      парах Up+Down.
- [ ] Зафіксований merge-спред на пару ≈ 1–2¢ (збігається з виміром книги).
- [ ] Гола експозиція лишається обмеженою й малою.
- [ ] Без падінь / без завислих котирувань / без розгону ризику.
Якщо щось із цього не виконується — припущення про латентність/чергу хибне; полагодити
перед §7.

## 7. Розрив до live-режиму (НЕ збудовано — потрібне явне рішення)
Зараз бот **навмисно лише paper**. До реальних грошей це треба збудувати й ретельно
перевірити (кожен пункт — окремий, окремо схвалений крок):
- [ ] Шлях live-виконання (реальне розміщення/скасування ордерів через автентифікований
      CLOB) — зараз `LiveExecutor`-заглушка; потребує наскрізного тестування.
- [ ] On-chain **CTF `mergePositions`** транзакція (Polygon), вшита в merge-крок.
- [ ] Профінансований proxy-гаманець + чотири `.env`-креденшіали API (лише за іменами).
- [ ] **Старт із мінімуму:** найменші розміри, низький `per_market_cap_usd`, жорсткий
      `max_daily_loss_usd`; довести плюсовий реалізований PnL на малому live-обсязі,
      перш ніж масштабувати. Перший live-капітал — це плата за навчання.

## Підсумок go / no-go
us-east-1 лагодить домінантну проблему (латентність → токсична гола нога). Це
**необхідно, але не достатньо**: ще потрібні сприятливі черга/комісії (§3), чиста
валідація paper на сервері (§6) і обережний малий live-запуск (§7). Не масштабувати,
поки §6 не пройде, а §7 не покаже плюсовий реалізований PnL на малому live-обсязі.
